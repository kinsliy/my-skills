# clarify-task-executor

## 0. 定位（一句话）

读 `./tasks/<YYYY-MM-DD>_xxx.md` → 实施 → 自验。
仅追加 task.md 末尾的「执行者增量区」（§E），**不改原作者 1~9 节一个字符**。
任何超出 task.md 范围的疑问 → 立即 `AskUserQuestion`（黄区流程）。

---

## 1. 触发与启动门禁

**触发**：用户说"开始执行 / 按 task.md 做 / 基于这份文档执行"且能定位到 `./tasks/<YYYY-MM-DD>_xxx.md`。

**门禁四条**（任一不通过 → 文本回复"请先用 requirement-clarify-first 完善并确认"，立即终止）：

- task.md 路径明确
- 含核心节：1 / 2 / 4 / 5 / 7
- 状态非 Draft / 空白
- 用户已显式表达执行意图

**禁止「边执行边补 md」原作者区** —— 缺失就回退澄清环节。

---

## 2. §E 执行者增量区（追加在 task.md 最末尾）

### 2.1 区段标识（必须照抄）

```markdown


---
---
<!-- =============== EXECUTOR APPEND ZONE (managed by clarify-task-executor) =============== -->
# 执行者增量区（Executor Append Zone）
> 由 `clarify-task-executor` 维护；原作者勿编辑。
```

### 2.2 简单模式（默认）—— 适用于净增量 ≤30 行 / 单文件 / 无新依赖

仅写 §E.1 + §E.5 两节即可：

```markdown
## E.1 todolist
- [ ] step 1
- [ ] step 2

## E.5 验收复核（含代码 deep link）
| 第 7 节条目 | 复核方式（[basename](file:///abs#L起-L止)） | 结果 |
```

### 2.3 复杂模式 —— 触发条件：跨文件 / 引入新常量 or 依赖 / 范围调整 / 同类失败 ≥1 次

新增 §E.2（决策）+ §E.3（用户追加 Q&A）+ §E.4（自检）+ §E.6（改动文件清单）。

```markdown
## E.2 决策（仅记录 task.md 未明说的小决策；Why 列写"为什么不选另一种"，禁止重复 What）
| 时间 | 决策点 | 选择 | 理由（why） |

## E.3 用户追加 Q&A（仅黄区触发时填）
| # | 触发场景 | 问题摘要 | 用户回答 | 落地方式 |

## E.4 自检（任一未过禁止交付）
- [ ] 仅做 4.1 IN，未越 4.2 OUT
- [ ] 覆盖 §5 边界
- [ ] 主入口加变更留痕（真实 date）
- [ ] 命名 / 长度 / 嵌套符合模块 D
- [ ] §E.5 每条挂代码 deep link（无对应代码注明"手测"）

## E.6 改动文件清单
- [文件 1](file:///...)
```

### 2.4 写入约束

- 只用 `Edit`/`Write` 维护本区段；区段外一字不动
- 重跑场景沿用同一区段，不重复追加分隔线

---

## 3. 工作流（顺序不可调）

### Step 1 — Observe + Counter-Verify

1. 完整读 task.md 全 9 节（不跳读）。
2. 按 §2 / §3 锚点 Read 涉及文件 + LS 同目录联动文件。
3. **反证 checklist**（命中任一不一致 → 立即进入 §4 黄区）：
   - [ ] 字段派生：IN 中的字段是否真的"独立输入"（非衍生）？
   - [ ] 锚点真实：task.md 提到的文件 / 函数 / 字段名是否真实存在且命名一致？
   - [ ] 同目录联动：入口文件同目录是否藏有 task.md 漏写的联动逻辑？
   - [ ] 下游消费链：IN 是"清空 / 重置 / 同步"语义时，所有消费侧（提交载荷构造、校验、序列化、watch）是否对实施手段产出的值都视为等价？
   - [ ] 参考实现：第 3 节让"1:1 对齐已有写法"时，已有写法本身是否真的达成 IN？
   - [ ] 上游字段：task.md 引用的外部返回字段（`res.data.xxx` 等）是否能在仓库定位到？找不到 → 黄区询问，禁止假设字段存在。
4. 在 task.md 末尾建 §E 区段骨架（按 §2.2 简单模式起步；触发 §2.3 条件再扩成复杂模式）。

### Step 2 — Analyze

- 把 4.1 IN 每条对应到代码段；把 §5 边界每条对应到代码会被命中处。
- 不影响 4.1/4.2/5/7 的小决策 → §E.2；影响 4.1/4.2/5/7 → §4 黄区。

### Step 3 — Plan

`TodoWrite` 列计划，**同步**写入 §E.1（双端勾选）。计划末态须对齐 §7 验收 + §5 代码层验证。

### Step 4 — Execute（三色契约 · 必读）

| 颜色 | 行为 | 典型 |
|------|------|------|
| 🟢 绿区 | 自由做，事中登记 §E.2，不打断用户 | 加临时变量 / 拆子函数 / 调整传参 / 选 hook 写法 / 抽公共纯函数（3 处再抽象） |
| 🟡 黄区 | 立即停下走 §4 | task.md 描述与事实不符 / IN 多义 / §5 边界漏 / §7 验收跑不通 / §8 风险新增 / 规范冲突 |
| 🔴 红区 | 严禁 | 改 4.2 OUT / 改 §7 验收 / 改原作者 1~9 节 / 违反用户全局规则 / 未授权 git 或全量构建 |

口诀："为达成 IN 必经？" → 绿区放手；"事实不符或多义？" → 黄区停下问；"触红线？" → 严禁。

**用户全局规则强约束**（必走）：A.1 最小改动 / A.6 变更留痕（主入口单行 + 真实 date）/ A.8 反过度工程 / C.2 孤儿代码清理 / D 命名 snake_case·函数 ≤20 行·参数 ≤3·嵌套 ≤3 / E.1 注释 why 优先 / E.2 中文日志 / K 性能（循环禁 IO·分页·事务·防抖节流）。

### Step 5 — Validate + Self-Critique

按 §7 逐条验证（优先级：单测 > 复现脚本 > 手测）。
**手测警戒**：IN 涉及"清空 / 删除 / 同步"且只做 UI 手测时，必须额外抓提交载荷（Network 或 `console.log(formData)`）确认 payload 中无残留 key。
对照 §E.4 自检逐项打勾；任一未过 → 回 Step 4。
通过后写入 §E.5 / §E.6 → 进入 §6 交付。
**失败处理**：回滚到稳定基线 → §E.2 记失败原因 → 同类失败 ≥2 次：先**升级到方案层**自问"是不是库 / 技术选型 / API 本身不支持当前场景"（而非继续在实现细节上反复打补丁），再走 §4 求助，且候选选项**必须含『换库 / 换技术方案』**一项（如某库流式读不支持某格式 → 换用支持的库）。

---

## 4. 黄区流程（一致性疑问处理）

仅 🟡 黄区走本流程。🟢 绿区登记 §E.2 即可；🔴 红区直接拒绝，不通过提问"开口子"。

**触发场景**（命中即停）：现状不符 / 上游字段无法证实 / 衍生字段被误列入 IN / 锚点缺失 / 范围歧义 / 边界遗漏 / 与 OUT 冲突 / 验收无法执行 / 风险新增 / 规范冲突。

**协议**：

1. `AskUserQuestion` 一次 ≤4 题；问题文字必须引用 task.md 节号 + 给出 ≥2 候选选项 + 用 `[basename](file:///...#L..)` 指明代码现状。
2. 用户回答前禁止编码（但可 Edit §E.3 登记问题）。
3. 用户回答后：登记 §E.3；小决策同步落 §E.2 + 代码注释；范围 / 边界变更**不要自己改原作者区**，文本提示用户回退澄清者更新或显式授权按本次回答继续。

---

## 5. 代码层验证

按优先级：单测（首选）→ 复现脚本（项目无测试框架时，存 `./tasks/<basename>.verify.<ext>`）→ 手测（仅前两者不可行时）。
**手测警戒**：见 Step 5。
执行边界：项目内已有脚本可 RunCommand（先在 §E.5 登记）；全量构建 / 部署 / `git commit/push` **需用户显式授权**。

---

## 6. 交付

仅普通文本回复：

- 改动文件清单（与 §E.6 一致）
- §7 逐项复核结论（与 §E.5 一致）
- §E.2 决策摘要 + §E.3 范围调整摘要（如有）
- 单测 / 复现脚本路径与跑法

禁止：`NotifyUser` / `PureShowWidget` / 未授权 git 操作。

---

## 7. 工具速查

| 工具 | 允许 | 备注 |
|---|---|---|
| `Read` `Grep` `Glob` `SearchCodebase` | ✅ | Step 1/2 充分读 |
| `TodoWrite` | ✅ | 与 §E.1 双端同步 |
| `Edit` `Write` `DeleteFile` | ✅ | 业务代码无黄区疑问后才动；§E 区段随时可 Edit |
| `Edit` task.md 原作者 1~9 节 | ❌ 严禁 | |
| `RunCommand date` | ✅ | 仅取真实本地时间 |
| `RunCommand` 已有测试 / 复现命令 | ✅ | 先登记 §E.5 |
| `RunCommand` 构建 / 部署 / git | ❌ 默认严禁 | 需用户授权 |
| `AskUserQuestion` | ✅ §4 时使用 | 一次 ≤4 |
| `NotifyUser` `PureShowWidget` | ❌ 严禁 | 触发"确认执行"按钮 |

---

## 8. 反 / 正例（极简）

❌ 改原作者区 / 跳过反证 checklist 直接复制粘贴参考实现 / 失败后在错误代码上打补丁 / 自跑 git commit / IN 涉提交载荷只做 UI 手测。
✅ 反证 checklist 命中即 §4 询问 → 用户回答后落 §E.2/§E.3 → 三色契约下编码 → 单测 + payload 抓包 → §E.4/§E.5 收尾 → 普通文本汇报。
