# requirement-clarify-first

## 0. 定位（一句话）

把模糊的"我要做 xxx"通过结构化提问拆解到信息充分，落地一份**自包含、可被下一个 AI 直接执行**的 task.md。
**只澄清不执行**；交付仅用普通文本回复，禁止任何会触发 IDE「确认执行」按钮的工具（见 §4）。

---

## 1. 触发

新需求 / bug 修复 / 审查（Disprove Mode）/ 重构 —— 满足任一即调用本 skill。

---

## 2. 工作流（顺序不可调）

### Step 0 — 先读后问（强制）

禁止直接 AskUserQuestion。围绕硬锚点（路径/字段/报错）做 1~3 次低成本读码：

- `Read` 硬锚点 + `LS` 同目录兄弟（hook/util/类型/上层组件）
- `Grep`/`SearchCodebase` 反查 1 次
- **写入点穷举**（IN 涉及"清空/同步/重置/校验/失效化"目标字段或状态时强制）：用 `Grep`/`SearchCodebase` 列出**目标的所有写入/变更入口**，1:1 检查是否都伴随预期副作用（如校验刷新、缓存失效、事件派发、依赖联动），结果产出到 §2 现状。适用于任意技术栈（前端 setState / 后端 ORM update / Redux dispatch / DB trigger 等）。
- 分清「已知（代码可读）」「未知（必须问）」两栏；已知禁止反问

### Step 1 — 反复提问（每轮 1~4 题）

按需问清以下维度（缺哪问哪，不全问）：
业务目标 / 现状 / **字段派生关系（多字段任务必问）** / 参考实现 / IN / OUT / 边界 / 验收 / 方案权衡 / 回滚。

> 衍生字段（由其他字段派生 / 联动）禁止列入 4.1 IN，应放进 §2 现状描述其联动来源。

### Step 2 — TodoWrite

仅列「创建 task.md → 通知用户复核」两步，不列执行相关动作。

### Step 3 — 写 task.md

- 路径：`./tasks/<YYYY-MM-DD>/<YYYY-MM-DD>_<prefix>_<task_basename>.md`（**日期必须先 RunCommand `date "+%Y-%m-%d"` 取真实本地时间**）。
- **目录创建规则**：写文件前先 `LS ./tasks/` 检查 `<YYYY-MM-DD>/` 目录是否存在；不存在则用 `RunCommand mkdir -p ./tasks/<YYYY-MM-DD>` 新建；存在则直接写入该目录。
- **文件名前缀（强制 11 选 1，无法归类时停下询问用户，禁止自创）**：
  - `fix`（修 bug）/ `feat`（新增功能）/ `refactor`（重构）/ `review`（审查/Review）/ `eval`（评估/调研）/ `spec`（需求澄清/设计）/ `docs`（文档）/ `perf`（性能优化）/ `test`（测试）/ `style`（样式/UI 微调）/ `chore`（构建/配置）
- **`<task_basename>` 长度限制：除前缀外最多 5 个单词**，单词间用 `_` 连接，全小写 snake_case；超过必须精简概括。
- **文档内一级标题（`# xxx`）必须含中文、一眼可读**：格式为 `# <中文一句话描述任务> (<prefix>_<task_basename>)`，中文部分直陈"修/加/审什么"，末尾括号附英文 basename 便于与文件名对照。禁止纯英文标题。
  - 正例：`# 修复表单子类型切回后模块未标记完成 (fix_sub_type_switch_residual_pending)`
- 审查类额外产出 `./tasks/<YYYY-MM-DD>/<YYYY-MM-DD>_review_<task_basename>_conclusion.md`。
- 写作禁忌：禁伪代码 / 禁改动清单 / 禁输入输出契约 / 禁 todolist 快照 / 禁变更留痕 / 禁把衍生字段写进 IN。

> 文件名示例：`./tasks/2025-01-15/2025-01-15_fix_form_residual.md`、`./tasks/2025-01-15/2025-01-15_review_translate_alignment.md`
> 同日同主题需迭代时，加 `_v2` 后缀（不要覆盖前一版）：`2025-01-15_fix_form_residual_v2.md`

## 3. task.md 模板（9 节，缺一不可；§0 条件生成）

```markdown
# <中文一句话描述任务> (<prefix>_<task_basename>)

> 元信息：类型 / 创建时间（真实 date）/ 优先级 / 工作量 / 状态

## 0. PRD 对照矩阵（**条件生成**：仅当任务存在外部需求文档锚点时必填，无锚点整节删除）

> 触发条件（满足任一）：① 用户给出 PRD/RFC/Spec/需求文档链接；② 任务前缀为 `feat`/`spec` 且用户描述里出现"需求 N""PRD 第 X 条""验收点 X"等可枚举要求点；③ 审查类（`review`）任务有对照对象。
> 不触发：纯 `fix` bug 修复 / `refactor` 内部重构 / `perf` 性能 / `chore` 配置 等没有"逐条要求点"概念的任务。
>
> **作用域口径（关键，避免越界）**：本表只对齐**当前任务作用域内**的 PRD 要求点。若源文档同时承载多个独立需求（如"需求一/二/三"），而本任务被拆到只做其中一个，则**只列被认领的那部分**；其它需求按"已拆到独立分支，不属于本任务"处理，**不进表**。
> "已认领需求内部"被拆到外部协同处理的项（如邮件模板配置由用户自行配）仍要进表，标 ❌ + 备注 OUT 理由，便于双向反证。
>
> 形式：6 列举证式 1:1 表格，每行一个原文要求点。
>
> 文档/需求来源：<填 URL 或锚点；多源逐条列出；如仅截取大文档某个子需求，明示"仅截取「需求 N」部分作为本任务 PRD">

| # | 需求原文要点（精炼引用，保留关键词） | 现状（改动前） | 是否覆盖 | 落点（§N 章节 + Deep Link） | 备注 / 反证依据 |
|---|---|---|---|---|---|
| 1 | 例：订单完成后通知接收人增加"运营管理员"角色 | 现接收人仅含负责人（[`xxx.js#L450`](file:///abs/xxx.js#L450)） | ✅ | §4.1 第 1 条；§6.2 改点 3；落点 [`xxx.js#L450`](file:///abs/xxx.js#L450) | 1:1 仿 notify_on_done 取数 |
| 2 | 例：上级为高阶角色时跳过该审批节点 | 节点无角色判断，无脑写入 | ✅ | §2.5；§6.2 改点 2 步骤 4 | 复用 `check_user_is_high_level_role` |
| 3 | 例：通知标题/中英文文案/变量调整 | 现模板含 `{{name}}` 等旧变量 | ❌ | — | OUT：通知模板配置，由用户自行处理（§4.2） |

> **校验规则**：表中每条 ✅ 必须能在下面 §N 中找到具体落点（Deep Link 或 §X.Y 章节号）；如发现 ✅ 后正文未落，立刻回 Step 1 补齐或降级为 ❌。

## 1. 背景与目标
- 业务背景（为什么做、谁在用）
- 目标（一句话期望结果 + 完成后可观测变化）

## 2. 现状与上下文
文件锚点 + 上下游依赖 + 历史包袱。**衍生字段的联动关系写在这里**。

## 3. 参考实现
类比模块路径 + 对齐策略（1:1 / 部分 / 仅思路）。

## 4. 范围
### 4.1 ✅ IN（业务产出，禁止写实施步骤、禁止写衍生字段）
### 4.2 ❌ OUT（明确不做 + 理由）

## 5. 边界场景与异常
空值 / 极端值 / 并发 / 网络异常 / 权限缺失 / 回滚。

## 6. 方案设计（**有条件生成**）
- 6.1 方案权衡：仅 ≥2 个真实可选方案时保留，否则整节删除
- 6.2 实施思路：仅必须钉死路径时保留，否则整节删除
- 永远禁止伪代码

## 7. 可验证成功标准
bug → 复现路径；功能 → ≥1 验证用例；重构 → 行为基线；审查 → 1:1 checkbox。

## 8. 风险与回滚

## 9. 信息确认日志
| # | 问题 | 用户回答 | 决策 |
```

## 4. 自检 + 交付

写完 task.md 后逐条自问，任一答否回到 Step 1/3 补齐：

- 下一个 AI 看完知道**业务意图与产出**吗？知道**怎么验证 / 不做什么 / 参考哪些模块**吗？
- 是否误写了伪代码 / 改动清单 / 输入输出契约 / todolist 快照 / 变更留痕？
- 4.1 IN 是否都是业务产出且无衍生字段？
- Step 0 是否读过硬锚点 + 同目录兄弟？涉清空/同步/重置/校验是否做过**写入点穷举**？
- IN 描述「现象」类时，§2 是否给出「现象 → 入口函数」多对一映射，避免下游只命中一个入口？
- 第 6 节是否违反"有条件生成"规则？
- **§0 PRD 对照矩阵**：是否命中触发条件？命中则必须存在；未命中（如纯 bug 修复 / 重构）则必须**整节删除**，不留空表。
- §0 表中**每条 ✅ 是否都能在下方 §N 找到对应落点**（Deep Link 或 §X.Y 章节号）？发现"✅ 但正文未落"则视为漏项，回 Step 1/3 补齐。
- 创建时间是否取自真实 `date`？文件名是否符合 `<YYYY-MM-DD>_<prefix>_<task_basename>.md` 格式？前缀是否在 11 选 1 范围内？basename 是否 ≤5 个单词？是否落入 `./tasks/<YYYY-MM-DD>/` 子目录（不存在则已创建）？
- 文档内一级标题是否含中文、一眼能看出干啥，并在末尾括号附英文 basename？（禁止纯英文标题）

**交付**：仅普通文本告知 `./tasks/<YYYY-MM-DD>/<YYYY-MM-DD>_<prefix>_xxx.md` 路径，请用户复核。**禁止**调用 `NotifyUser` / `PureShowWidget` / `AskUserQuestion`（这一步会触发 IDE 确认按钮）。

**工具约束**：

- ✅ `Read` `LS` `Glob` `Grep` `SearchCodebase`（Step 0 必用）
- ✅ `AskUserQuestion`（仅 Step 1）`TodoWrite`（Step 2）`RunCommand date`（取真实时间）`RunCommand mkdir -p`（创建日期目录）`Write`（生成 task.md）
- ❌ `NotifyUser` / `PureShowWidget` / 任何业务代码编辑工具

---

## 5. 反 / 正例（极简）

❌ 跳过 Step 0 直接 AskUserQuestion；把代码可读出的字段问回用户；写完后调 NotifyUser；文件名不带日期 / 不带前缀 / 前缀自创 / basename 超 5 词 / 文件直接写在 `./tasks/` 根目录。
✅ Step 0 读硬锚点 + 同目录 → Step 1 仅问"未知" → RunCommand 取 date → LS 检查 `./tasks/<YYYY-MM-DD>/` → 不存在则 `mkdir -p` → Write `./tasks/<YYYY-MM-DD>/<YYYY-MM-DD>_<prefix>_xxx.md` → 普通文本请用户复核。
